\chapter{OpenTelemetry Collector Konfiguration}
\label{app:otel-collector}

Alle nachfolgenden Konfigurationsdateien, Alert-Regeln und Runbooks sind auch im öffentlichen Repository verfügbar.\footnote{\url{https://github.com/LeonRau03/frag.jetzt-observability}} Die folgende Datei zeigt die vollständige Konfiguration des OpenTelemetry Collector (Version~0.120.0), wie sie auf dem Staging-Server von frag.jetzt eingesetzt wird. Die Konfiguration definiert die Empfangs-, Verarbeitungs- und Exportpipelines für alle drei Telemetriearten.

Der \texttt{filter/traces}-Processor (Zeilen~16--28) ist die zentrale projektspezifische Anpassung. Er verwirft acht namentlich benannte Span-Typen, die von periodischen Hintergrundprozessen erzeugt werden und keinen diagnostischen Wert für die Fehlersuche besitzen (vgl.\ Abschnitt~7.5.3). Dieser Ansatz ersetzt ein probabilistisches Sampling durch eine inhaltlich begründete Selektion.

\begin{lstlisting}[style=yamlstyle, caption={OpenTelemetry Collector Konfiguration (\texttt{config.yaml}).}, label={lst:otel-config}]
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    send_batch_size: 1024
    timeout: 5s
  resource:
    attributes:
      - key: deployment.environment
        value: staging
        action: upsert
  memory_limiter:
    check_interval: 5s
    limit_mib: 200
    spike_limit_mib: 50
  filter/traces:
    error_mode: ignore
    traces:
      span:
        - 'name == "ScheduledMessageSender.send"'
        - 'name == "LivepollEventSource.sendAndUpdate"'
        - 'name == "ScheduledMessageSender.sendToTopic"'
        - 'name == "UserRegistryTask.run"'
        - 'name == "MailScheduler.onTick"'
        - 'name == "CommentNotificationService.sendNotifications"'
        - 'name == "clientInboundChannel process"'
        - 'name == "clientOutboundChannel process"'

exporters:
  otlphttp/prometheus:
    endpoint: http://prometheus:9090/api/v1/otlp
    tls:
      insecure: true
  otlphttp/loki:
    endpoint: http://loki:3100/otlp
    tls:
      insecure: true
  otlp/tempo:
    endpoint: tempo:4317
    tls:
      insecure: true
  debug:
    verbosity: basic
    sampling_initial: 5
    sampling_thereafter: 200

extensions:
  health_check:
    endpoint: 0.0.0.0:13133

service:
  extensions: [health_check]
  pipelines:
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, resource, batch]
      exporters: [otlphttp/prometheus, debug]
    logs:
      receivers: [otlp]
      processors: [memory_limiter, resource, batch]
      exporters: [otlphttp/loki, debug]
    traces:
      receivers: [otlp]
      processors: [memory_limiter, filter/traces, resource, batch]
      exporters: [otlp/tempo, debug]
  telemetry:
    logs:
      level: info
\end{lstlisting}

\chapter{Alerting-Regeln}
\label{app:alerting-rules}

% Sorgt bei run-in-\paragraph fuer einen sauberen Zeilenumbruch vor Listings.
\newcommand{\promqlheading}[1]{\paragraph{#1}\leavevmode\par\vspace{0.25\baselineskip}}

Die folgenden drei Alerting-Regeln wurden in Grafana Alerting konfiguriert und bilden die prototypische Umsetzung des in Abschnitt~6.5 konzipierten Alerting-Frameworks. Alle Regeln verwenden Multi-Signal-Logik, bei der ein primäres Fehlersignal erst in Kombination mit einer Mindest-Traffic-Rate als handlungsrelevant gewertet wird (vgl.\ Abschnitt~7.4).


\section{Alert~1: User-facing Latency Degradation}

\begin{description}[style=sameline, leftmargin=5.4cm, labelwidth=4.6cm, labelsep=0.8cm]
  \item[Severity] Warning
  \item[Primäre Rolle] DevOps
  \item[Zugehöriges Runbook] Erhöhte Backend-Latenz (Anhang~\ref{app:runbook-latenz})
\end{description}

\paragraph{Logik.}
Der Alert feuert, wenn \emph{beide} Bedingungen gleichzeitig für mindestens drei Minuten erfüllt sind:
\begin{enumerate}
  \item Die Backend-Antwortzeit im 95.\ Perzentil überschreitet 500\,ms.
  \item Die Anfragerate liegt über 0{,}1\,req/s (kein Leerlauf).
\end{enumerate}

\promqlheading{PromQL -- Condition~A (Latenz).}
\begin{lstlisting}[style=bashstyle, numbers=none]
histogram_quantile(0.95,
  sum(rate(
    http_server_request_duration_seconds_bucket{
      job="fragjetzt-backend"
    }[5m]
  )) by (le)
) > 0.5
\end{lstlisting}

\promqlheading{PromQL -- Condition~B (Mindest-Traffic).}
\begin{lstlisting}[style=bashstyle, numbers=none]
sum(rate(
  traces_spanmetrics_calls_total{
    service="fragjetzt-backend",
    span_kind="SPAN_KIND_SERVER"
  }[5m]
)) > 0.1
\end{lstlisting}

\paragraph{Grafana-Konfiguration.}
Evaluation Group: \texttt{golden-signals}, Evaluation Interval: 1\,min, Pending Period: 3\,min, Condition: A~\texttt{AND}~B.

\paragraph{Annotations.}
\emph{Summary:} Backend-Antwortzeit erhöht (p95~>~500\,ms). \emph{Description:} Die Antwortzeit des Backends im 95.\ Perzentil liegt seit über drei Minuten über 500\,ms bei aktivem Traffic. Nutzende können Verzögerungen bei Frageerstellung, Abstimmungen oder Raumnavigation wahrnehmen.

\paragraph{Labels.}
\texttt{severity: warning}, \texttt{service: fragjetzt-backend}, \texttt{signal: latency}, \texttt{stakeholder: devops}.


\bigskip
\section{Alert~2: Backend Error Spike}

\begin{description}[style=sameline, leftmargin=5.4cm, labelwidth=4.6cm, labelsep=0.8cm]
  \item[Severity] Critical
  \item[Primäre Rolle] Developer
  \item[Zugehöriges Runbook] Erhöhte Fehlerquote / HTTP~5xx (Anhang~\ref{app:runbook-fehlerquote})
\end{description}

\paragraph{Logik.}
Der Alert feuert, wenn \emph{beide} Bedingungen gleichzeitig für mindestens drei Minuten erfüllt sind:
\begin{enumerate}
  \item Die HTTP-5xx-Fehlerrate des Backends überschreitet 5\,\%.
  \item Die Anfragerate liegt über 0{,}1\,req/s.
\end{enumerate}

\promqlheading{PromQL -- Condition~A (Fehlerrate).}
\begin{lstlisting}[style=bashstyle, numbers=none]
(
  sum(rate(
    http_server_request_duration_seconds_count{
      job="fragjetzt-backend",
      http_response_status_code=~"5.."
    }[5m]
  ))
  /
  clamp_min(sum(rate(
    http_server_request_duration_seconds_count{
      job="fragjetzt-backend"
    }[5m]
  )), 1e-9)
) > 0.05
\end{lstlisting}

\promqlheading{PromQL -- Condition~B (Mindest-Traffic).}
\begin{lstlisting}[style=bashstyle, numbers=none]
sum(rate(
  http_server_request_duration_seconds_count{
    job="fragjetzt-backend"
  }[5m]
)) > 0.1
\end{lstlisting}

\paragraph{Grafana-Konfiguration.}
Evaluation Group: \texttt{golden-signals}, Evaluation Interval: 1\,min, Pending Period: 3\,min, Condition: A~\texttt{AND}~B.

\paragraph{Annotations.}
\emph{Summary:} Backend-Fehlerrate kritisch erhöht (5xx~>~5\,\%). \emph{Description:} Mehr als 5\,\% der Backend-Anfragen liefern HTTP-5xx-Fehler bei aktivem Traffic. Betroffene Endpunkte können über die Errors-Sektion des Dashboards und über Tempo (Trace-Suche, Status Error) identifiziert werden.

\paragraph{Labels.}
\texttt{severity: critical}, \texttt{service: fragjetzt-backend}, \texttt{signal: errors}, \texttt{stakeholder: developer}.


\bigskip
\section{Alert~3: Infrastructure Saturation with Service Impact}

\begin{description}[style=sameline, leftmargin=5.4cm, labelwidth=4.6cm, labelsep=0.8cm]
  \item[Severity] Warning
  \item[Primäre Rolle] DevOps
  \item[Zugehöriges Runbook] Infrastruktur-Sättigung (DB / Queue / Host) (Anhang~\ref{app:runbook-saettigung})
\end{description}

\paragraph{Logik.}
Der Alert feuert, wenn \emph{eine} der folgenden Variantenbedingungen für mindestens fünf Minuten erfüllt ist:

\emph{Variante~A (Datenbank-Sättigung):} PostgreSQL aktive Verbindungen~>~70 \textbf{und} Backend p95-Latenz~>~200\,ms.

\emph{Variante~B (Queue-Rückstau):} RabbitMQ Queue Messages~>~1000.

\promqlheading{PromQL -- Condition~A1 (DB Connections).}
\begin{lstlisting}[style=bashstyle, numbers=none]
sum(pg_stat_activity_count{
  job="postgres", state="active"
}) > 70
\end{lstlisting}

\promqlheading{PromQL -- Condition~A2 (Latenz-Bestätigung).}
\begin{lstlisting}[style=bashstyle, numbers=none]
histogram_quantile(0.95,
  sum(rate(
    http_server_request_duration_seconds_bucket{
      job="fragjetzt-backend"
    }[5m]
  )) by (le)
) > 0.2
\end{lstlisting}

\promqlheading{PromQL -- Condition~B1 (Queue Depth).}
\begin{lstlisting}[style=bashstyle, numbers=none]
sum(rabbitmq_queue_messages{job="rabbitmq"}) > 1000
\end{lstlisting}

\paragraph{Grafana-Konfiguration.}
Evaluation Group: \texttt{infrastructure}, Evaluation Interval: 1\,min, Pending Period: 5\,min, Condition: (A1~\texttt{AND}~A2)~\texttt{OR}~B1.

\paragraph{Annotations.}
\emph{Summary:} Infrastruktur-Sättigung mit Servicewirkung. \emph{Description:} Infrastrukturressourcen (Datenbankverbindungen oder Message Queue) nähern sich ihren Kapazitätsgrenzen und gleichzeitig zeigen Servicemetriken eine Verschlechterung. Ohne Gegenmaßnahmen kann die Störung auf weitere Dienste kaskadieren.

\paragraph{Labels.}
\texttt{severity: warning}, \texttt{service: infrastructure}, \texttt{signal: saturation}, \texttt{stakeholder: devops}.

\section{Runbook: Erhöhte Backend-Latenz}
\label{app:runbook-latenz}

\begin{description}[style=nextline, leftmargin=3.5cm]
  \item[Incident-Typ] User-facing Latency Degradation
  \item[Trigger] Alert \enquote{Backend p95-Latenz~>~500\,ms bei aktivem Traffic} feuert seit $\geq$~3~Minuten.
\end{description}

\paragraph{Nutzerwirkung.}
Verzögerungen bei interaktiven Aktionen wie Frageerstellung, Abstimmungen und Raum-Navigation. Bei Lehrveranstaltungen mit synchroner Nutzung sind viele Teilnehmende gleichzeitig betroffen.

\paragraph{Relevante Signale.}

\begin{table}[H]
\centering
\small
\begin{tabularx}{\textwidth}{l l >{\RaggedRight\arraybackslash}X}
\toprule
\textbf{Signal} & \textbf{Dashboard-Panel} & \textbf{Erwartetes Verhalten} \\
\midrule
Backend p95/p99 Latenz & Latency $\rightarrow$ Backend HTTP Latency & Anstieg über 500\,ms \\
Request Rate & Traffic $\rightarrow$ Request Rate by Service & Aktiver Traffic ($>$~0{,}1\,req/s) \\
Latenz pro Endpunkt & Latency $\rightarrow$ Latency by Endpoint & Einzelne Endpunkte auffällig \\
DB Connection Count & Infrastructure $\rightarrow$ PostgreSQL Active Conn. & Möglicherweise erhöht \\
JVM Heap / GC & Saturation $\rightarrow$ JVM Heap / GC Pause & Möglicherweise erhöht \\
\bottomrule
\end{tabularx}
\end{table}

\paragraph{Sofortmaßnahmen (0--5~Minuten).}

\emph{DevOps (primäre Rolle):}
\begin{enumerate}
  \item Dashboard öffnen: Golden Signals $\rightarrow$ Latency-Sektion prüfen.
  \item Scope eingrenzen: Betrifft die Latenz alle Endpunkte oder nur bestimmte? Panel \enquote{Latency by Endpoint (p95)} prüfen.
  \item Infrastruktur prüfen: Host-Ressourcen (CPU~$>$~80\,\%? Memory~$>$~90\,\%?), PostgreSQL (Verbindungen nahe 100?), RabbitMQ (Queue-Rückstau?).\\
  \item Container-Status prüfen:
\begin{lstlisting}[style=bashstyle]
sudo docker ps --format "table {{.Names}}\t{{.Status}}" \
  | grep fragjetzt
sudo docker stats --no-stream | head -15
\end{lstlisting}
\end{enumerate}

\emph{Developer (sekundäre Rolle):}
\begin{enumerate}
  \item Trace-Analyse: Grafana $\rightarrow$ Explore $\rightarrow$ Tempo $\rightarrow$ Search. Filter: Service~=~\texttt{fragjetzt-backend}, Duration~$>$~500\,ms. Span-Waterfall öffnen und prüfen, wo der Request die meiste Zeit verbringt.
  \item DB-Spans prüfen: R2DBC-Spans (SELECT/UPDATE) mit Laufzeit $>$~50\,ms identifizieren.
  \item Logs korrelieren: Vom langsamen Trace über die Funktion \emph{Logs for this span} zu den zugehörigen Loki-Logs navigieren.
\end{enumerate}

\paragraph{Diagnosepfad (5--15~Minuten).}

\emph{Mögliche Ursache~1: Datenbankengpass.} Indikator: DB-Spans im Trace $>$~50\,ms, PostgreSQL Connections~$>$~70. Prüfung:
\begin{lstlisting}[style=bashstyle]
sudo docker exec fragjetzt-postgres psql -U fragjetzt -c \
  "SELECT state, count(*) FROM pg_stat_activity
   GROUP BY state;"
sudo docker exec fragjetzt-postgres psql -U fragjetzt -c \
  "SELECT pid, now()-query_start AS duration, query
   FROM pg_stat_activity WHERE state='active'
   ORDER BY duration DESC LIMIT 5;"
\end{lstlisting}
Maßnahme: Langlaufende Queries identifizieren und gegebenenfalls terminieren.

\emph{Mögliche Ursache~2: JVM-Ressourcenerschöpfung.} Indikator: GC Pause Duration steigt, Heap nahe Limit. Maßnahme: Backend-Container neu starten.
\begin{lstlisting}[style=bashstyle]
cd /opt/containers/staging_frag_jetzt/\
  frag.jetzt-docker-orchestration
sudo docker compose restart backend
\end{lstlisting}

\emph{Mögliche Ursache~3: Externe Abhängigkeit (Keycloak, KI-Dienst).} Indikator: Trace zeigt langen ausgehenden HTTP-Span. Prüfung: Span-Details im Trace, Ziel-URL und Dauer. Maßnahme: Betroffenen Upstream-Dienst prüfen oder Request-Pfad isolieren.

\paragraph{Eskalation.}
Wenn die Latenz nach 15~Minuten nicht sinkt: Hauptentwickler kontaktieren. Bei Totalausfall: Proxy-Level-Wartungsseite aktivieren.

\paragraph{Kriterium für Entwarnung.}
Backend p95-Latenz unter 200\,ms für mindestens 5~Minuten, keine auffälligen Endpunkte im Latenz-Panel, PostgreSQL Connections im Normbereich ($<$~30~aktive).
\clearpage

\section{Runbook: Erhöhte Fehlerquote / HTTP~5xx}
\label{app:runbook-fehlerquote}

\begin{description}[style=nextline, leftmargin=3.5cm]
  \item[Incident-Typ] Backend Error Spike
  \item[Trigger] Alert \enquote{HTTP-5xx-Rate~>~5\,\% bei aktivem Traffic} feuert seit $\geq$~3~Minuten.
\end{description}

\paragraph{Nutzerwirkung.}
Nutzende erhalten Fehlermeldungen bei Interaktionen mit der Plattform. Betroffene Funktionen können Frageerstellung, Abstimmungen, Login oder KI-gestützte Features sein. Bei synchroner Nutzung führen sichtbare Fehler zu Vertrauensverlust und Unterbrechung des Veranstaltungsablaufs.

\paragraph{Relevante Signale.}

\begin{table}[H]
\centering
\small
\begin{tabularx}{\textwidth}{l l >{\RaggedRight\arraybackslash}X}
\toprule
\textbf{Signal} & \textbf{Dashboard-Panel} & \textbf{Erwartetes Verhalten} \\
\midrule
HTTP 5xx Rate & Errors $\rightarrow$ HTTP 5xx Rate (Backend) & Über 5\,\% \\
Error Rate by Service & Errors $\rightarrow$ Error Rate by Service & Backend-Linie steigt \\
Top Error Spans & Errors $\rightarrow$ Top Error Spans (5\,min) & Betroffene Operationen sichtbar \\
Request Rate & Traffic $\rightarrow$ Request Rate by Service & Aktiver Traffic bestätigt \\
Backend Logs & Loki $\rightarrow$ \texttt{\{service\_name=\char`\"fragjetzt-backend\char`\"\}} & Exception-Stacktraces \\
\bottomrule
\end{tabularx}
\end{table}

\paragraph{Sofortmaßnahmen (0--5~Minuten).}

\emph{Developer (primäre Rolle):}
\begin{enumerate}
  \item Fehlerquelle identifizieren: Golden Signals Dashboard $\rightarrow$ Errors-Sektion. Panel \enquote{Top Error Spans (5\,min)} prüfen und betroffene Funktionsbereiche eingrenzen (Q\&A, Voting, Auth, KI).
  \item Fehlerhafte Traces öffnen: Grafana $\rightarrow$ Explore $\rightarrow$ Tempo $\rightarrow$ Search (Service~=~\texttt{fragjetzt-backend}, Status~=~Error). Span-Waterfall analysieren: HTTP Status Code und Exception Message prüfen.
  \item Logs korrelieren: Vom fehlerhaften Trace zu Loki navigieren. Exception-Stacktraces lesen und Fehlermuster identifizieren.
\end{enumerate}
\clearpage
\emph{DevOps (sekundäre Rolle):}
\begin{enumerate}
  \item Container-Gesundheit prüfen:
\begin{lstlisting}[style=bashstyle]
sudo docker ps --format "table {{.Names}}\t{{.Status}}" \
  | grep fragjetzt
sudo docker logs fragjetzt-backend --since 5m 2>&1 \
  | grep -i "error\|exception" | tail -20
\end{lstlisting}
  \item Letzte Änderungen prüfen: Gab es ein kürzliches Deployment oder eine Konfigurationsänderung?
  \item Abhängigkeiten prüfen: Sind PostgreSQL, RabbitMQ und Keycloak erreichbar?
\end{enumerate}

\paragraph{Diagnosepfad (5--15~Minuten).}

\emph{Mögliche Ursache~1: Datenbankverbindungsfehler.} Indikator: Error Spans enthalten \texttt{ConnectionException}, \texttt{R2dbcException} oder \texttt{TimeoutException}. Maßnahme: PostgreSQL-Container prüfen und gegebenenfalls neu starten.

\emph{Mögliche Ursache~2: Fehler in einem spezifischen Endpunkt.} Indikator: Top Error Spans zeigt einen einzelnen Endpunkt. Maßnahme: Bug-Report erstellen, gegebenenfalls betroffene Funktion temporär deaktivieren.

\emph{Mögliche Ursache~3: Externe Abhängigkeit nicht erreichbar.} Indikator: Error Spans auf ausgehenden HTTP-Calls (Keycloak, PayPal, LLM-Provider). Maßnahme: Externen Dienst prüfen, bei Nichterreichbarkeit Graceful Degradation erwägen.

\emph{Mögliche Ursache~4: Ressourcenerschöpfung.} Indikator: JVM Heap nahe Limit, OOM-Fehler in Logs. Maßnahme: Backend-Container neu starten.

\paragraph{Eskalation.}
Wenn die Fehlerrate nach Backend-Restart nicht sinkt: Hauptentwickler kontaktieren. Wenn mehrere Endpunkte gleichzeitig betroffen sind: systemweites Problem vermuten und alle Abhängigkeiten prüfen.

\paragraph{Kriterium für Entwarnung.}
HTTP 5xx Rate unter 1\,\% für mindestens 5~Minuten, keine neuen Error Spans in der Top-Error-Tabelle, Backend-Logs ohne wiederkehrende Exceptions.
\clearpage

\section{Runbook: Infrastruktur-Sättigung (DB / Queue / Host)}
\label{app:runbook-saettigung}

\begin{description}[style=nextline, leftmargin=3.5cm]
  \item[Incident-Typ] Database / Queue Saturation with Service Impact
  \item[Trigger] Alert \enquote{Infrastruktur-Sättigung mit Servicewirkung} feuert, wenn eine der folgenden Bedingungen seit $\geq$~5~Minuten erfüllt ist: (a)~PostgreSQL aktive Verbindungen~$>$~70 \textbf{und} Backend p95-Latenz~$>$~200\,ms, oder (b)~RabbitMQ Queue Messages~$>$~1000 dauerhaft.
\end{description}

\paragraph{Nutzerwirkung.}
Verzögerungen oder Ausfälle bei datenbankgestützten Funktionen (Frageerstellung, Abstimmungen, Raum-Verwaltung) oder bei Echtzeit-Updates über WebSocket (Live-Voting, Teilnehmerzählung). Die Störung kann von einer einzelnen Funktion auf weitere kaskadieren, wenn die Ressourcenerschöpfung zunimmt.

\paragraph{Relevante Signale.}

\begin{table}[H]
\centering
\small
\begin{tabularx}{\textwidth}{l l >{\RaggedRight\arraybackslash}X}
\toprule
\textbf{Signal} & \textbf{Dashboard-Panel} & \textbf{Erwartetes Verhalten} \\
\midrule
PostgreSQL Connections & Infrastructure $\rightarrow$ PostgreSQL Active Conn. & $>$~70~aktive \\
RabbitMQ Queue Depth & Infrastructure $\rightarrow$ RabbitMQ Messages & $>$~1000 oder steigend \\
Backend p95 Latenz & Latency $\rightarrow$ Backend HTTP Latency & Korreliert erhöht \\
Host Memory / CPU & Infrastructure $\rightarrow$ Host Memory \& CPU & Möglicherweise erhöht \\
JVM Thread Count & Saturation $\rightarrow$ JVM Thread Count & Möglicherweise erhöht \\
\bottomrule
\end{tabularx}
\end{table}

\paragraph{Sofortmaßnahmen (0--5~Minuten).}

\emph{DevOps (primäre Rolle):}
\begin{enumerate}
  \item Sättigungsquelle identifizieren: Dashboard $\rightarrow$ Infrastructure-Sektion. PostgreSQL Panel, RabbitMQ Panel und Host Panel prüfen.
  \item Container-Ressourcen prüfen:
\begin{lstlisting}[style=bashstyle]
sudo docker stats --no-stream \
  --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}" \
  | head -15
\end{lstlisting}
  \item PostgreSQL-Verbindungen im Detail prüfen:
\begin{lstlisting}[style=bashstyle]
sudo docker exec fragjetzt-postgres psql -U fragjetzt -c \
  "SELECT state, count(*),
          avg(now()-query_start) as avg_duration
   FROM pg_stat_activity
   WHERE datname = 'fragjetzt'
   GROUP BY state ORDER BY count DESC;"
\end{lstlisting}
  \item RabbitMQ-Queue-Status prüfen:
\begin{lstlisting}[style=bashstyle]
sudo docker exec fragjetzt-rabbitmq \
  rabbitmqctl list_queues name messages consumers
\end{lstlisting}
\end{enumerate}

\emph{Developer (sekundäre Rolle):}
\begin{enumerate}
  \item Langlaufende Queries identifizieren:
\begin{lstlisting}[style=bashstyle]
sudo docker exec fragjetzt-postgres psql -U fragjetzt -c \
  "SELECT pid, now()-query_start AS duration,
          left(query, 80) as query
   FROM pg_stat_activity
   WHERE state='active' AND datname='fragjetzt'
   ORDER BY duration DESC LIMIT 10;"
\end{lstlisting}
  \item Trace-Korrelation: Grafana $\rightarrow$ Tempo $\rightarrow$ Search. Traces mit langen DB-Spans ($>$~100\,ms) suchen und prüfen, ob ein bestimmter Endpunkt unverhältnismäßig viele Verbindungen verbraucht.
  \item Vote-Trigger prüfen (bekannter Engpass, vgl.\ Risikopunkt~R2): Sind viele parallele Abstimmungen aktiv? Zeigen Traces Row-Level Contention auf der \texttt{comment}-Tabelle?
\end{enumerate}

\paragraph{Diagnosepfad (5--15~Minuten).}

\emph{Mögliche Ursache~1: Connection-Pool-Erschöpfung.} Indikator: Aktive Verbindungen $>$~70, idle Verbindungen niedrig. Maßnahme: Idle-in-Transaction-Verbindungen beenden:
\begin{lstlisting}[style=bashstyle]
sudo docker exec fragjetzt-postgres psql -U fragjetzt -c \
  "SELECT pg_terminate_backend(pid)
   FROM pg_stat_activity
   WHERE state = 'idle in transaction'
     AND query_start < now() - interval '5 minutes';"
\end{lstlisting}

\emph{Mögliche Ursache~2: RabbitMQ-Consumer-Rückstand.} Indikator: Queue-Tiefe steigt, Consumer-Zahl niedrig oder null. Maßnahme: WS-Gateway-Container prüfen und gegebenenfalls neu starten (\texttt{docker compose restart ws-gateway}).

\emph{Mögliche Ursache~3: Host-Ressourcenverdrängung (R5).} Indikator: Host CPU $>$~80\,\% oder Memory $>$~90\,\%, mehrere Container betroffen. Maßnahme: Nicht-kritische Container temporär stoppen (z.\,B.\ AI Provider).

\emph{Mögliche Ursache~4: Lastspitze durch Lehrveranstaltung.} Indikator: Request-Rate und WebSocket-Verbindungen gleichzeitig hoch. Maßnahme: Situation beobachten. Die Sättigung sinkt nach Veranstaltungsende. Bei wiederholtem Auftreten Kapazitätsplanung einleiten.

\paragraph{Eskalation.}
Wenn PostgreSQL-Verbindungen nach Bereinigung erneut ansteigen: Hauptentwickler einbeziehen (möglicherweise Connection-Leak im Code). Wenn Host-Ressourcen dauerhaft erschöpft: Infrastruktur-Skalierung besprechen.

\paragraph{Kriterium für Entwarnung.}
PostgreSQL aktive Verbindungen unter 30, RabbitMQ Queue-Tiefe unter 100, Backend p95-Latenz unter 200\,ms, Host CPU unter 60\,\% und Memory unter 75\,\%.
